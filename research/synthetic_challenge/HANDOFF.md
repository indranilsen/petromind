## Session A: keep the model boundary narrow

1. Start one owner-side [trusted_host.py](integration/trusted_host.py) process per
   case with the public release path, private root and a fresh private audit path.
2. Give Muse only the first JSON response's `result`: that single public packet.
   Use a fresh context for every case; grant no filesystem/shell/repository tools.
3. Forward only the five documented tools as sequential JSON-lines requests;
   forward only each response's `result` back to Muse. The host mediates the
   shared five-sensor budget and bounded structural repairs.
4. After all model contexts close, assemble host audit files and run the unchanged
   private scorer in a separate owner-only process. Scores contain reference
   verdicts and must never return to Muse or guide changes during the benchmark.
5. Use the separate synthetic contract only for this model. Production v5 retains
   its supported-diagnostic rejection; do not route real-data investigations here.

The [integration guide](INTEGRATION_GUIDE.md) gives exact process-launch,
request/response, transcript assembly and scoring commands. The executable
[offline_smoke.py](integration/offline_smoke.py) demonstrates the complete flow
without a model or reference-guided assessment.

**Required isolation:** never give Muse the full public directory. Variants share
sensor traces; a channel hidden in one can be initially visible in another. The
per-case packets contain only initial readings and no private answer fields, and
graph responses contain no hidden samples. The bridge is a local transport, not an
OS sandbox: an agent with local file tools needs a separate UID/container from the
owner process. Selected sensor readings are released only by budgeted queries.
